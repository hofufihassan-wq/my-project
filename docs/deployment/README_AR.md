# V Lex Pro 1.0 — تجهيز Cloudflare Pages

**الحالة: تجهيز ومراجعة، وليس نشرًا.** لا يوجد حتى الآن رابط إنتاج Cloudflare مُتحقق منه. لم يُدمج هذا الفرع في main، ولم تتغير خصوصية المستودع أو إعداداته أو قواعد حمايته. نظام الدخول ذي الأرقام الستة مؤجل ولم يُنفذ.

## النسخة والتاريخ

جُلبت جميع الفروع البعيدة قبل العمل. أحدث نسخة مكتملة هي `feat/vlex-v1-followup` عند `b07ddcfddfaaf4654a4f3e0b569c915c676ab86f`، لا main. فرع main عند `535b1ae008b50a623016da04601ee34e5af84ea2`: بينهما 63 Commit في مسار الإكمال وCommit واحد منفرد في main، هو سير GitHub Pages القديم.

أُنشئ فرع `chore/vlex-pages-readiness` من نسخة الإكمال، وأُدخل فيه تاريخ main بدمج مستقل `a97a5fb`؛ لم يتحرك main. جميع Commits الأصلية محفوظة، ولا force push أو إعادة كتابة للتاريخ. ملفات تشغيل الموقع مطابقة لنسخة b07ddcf؛ التعديلات تخص النشر والاختبارات والتوثيق فقط.

المستودع نفسه ذو المعرف 1438045690، واسمه الحالي `hofufihassan-wq/my-project` وحالته Public والفرع الافتراضي main. عنوان my-progect القديم يعيد التوجيه إليه. بقاء المستودع Public جاء بتوجيه المستخدم الحالي؛ لم نغير خصوصيته.

|الإعداد|القيمة|

|المستودع|hofufihassan-wq/my-project|
|Framework preset|None|
|Root directory|جذر المستودع؛ اتركه فارغًا في الواجهة|

|Build output directory|`dist`|

|Python للبناء فقط|3.12.14 عبر `.python-version`|
|Environment variable|`SKIP_DEPENDENCY_INSTALL=1` لتشغيل تثبيت lockfile الصريح أعلاه مرة واحدة|
|مفاتيح أو أسرار تشغيل|لا توجد حاجة إلى مفاتيح API أو قاعدة بيانات أو KV أو R2 أو خدمات مدفوعة|

الإصدارات المحددة هي التي شُغّل بها البناء هنا، وتحققت إتاحتها في مستودعات Node وCPython الرسمية. وثائق Cloudflare v3 تدعم هذين الملفين وتخصيص الإصدارات؛ تبقى تجربة بناء Cloudflare الفعلية معلقة حتى الربط. لا يكفي engines في package.json لأن v3 لا تعتمد عليها لتحديد Node. لا ترفع جذر المستودع أو docs أو الاختبارات أو حزم ZIP؛ وزع dist فقط.

الملفات المولدة تحت dist مستبعدة من Git. الواجهات وVue وCompiler وVue Router وWorkers والمكتبات والخطوط محلية داخل التوزيع. Python وNode أدوات بناء، وليسا خدمة لازمة لزيارة الموقع. ملف `_headers` يحافظ على إعادة التحقق من الملفات مع التحديث ولا يضيف CSP عامة تكسر المعاينات.

## الخطوة التي تحتاج حساب المستخدم

1. افتح [Cloudflare Dashboard](https://dash.cloudflare.com/) وسجل الدخول إلى حسابك، واختر الخطة المجانية.
2. Workers & Pages ← Create application ← Pages ← Connect to Git، ثم اربط GitHub بتفويض هذا المستودع فقط.
3. **توقف قبل Save and Deploy.** main الحالي قديم، وإنشاء المشروع قد يبدأ نشره تلقائيًا. لا تستخدم main أو فرعًا آخر كتجربة إنتاج قبل الاعتماد.
4. بعد موافقتك على النسخة ومسألة خصوصية تاريخ المؤلفين، يُدمج فرع التجهيز في main، ثم تستكمل إعدادات الجدول وتبدأ عملية النشر.
5. أرسل رابط المشروع الفعلي الذي يعطيه Cloudflare، دون إرسال كلمة مرور أو رمز دخول أو API token في المحادثة.

لا يوجد موصل Cloudflare أو حساب مرتبط بهذه البيئة، والاتصال إلى Cloudflare وpages.dev غير مضاف لقائمة الشبكة. للتحقق من الرابط هنا بعد الربط، أضف اسم نطاق الإنتاج الفعلي واسم نطاق المعاينة الفعلي إلى إعدادات شبكة بيئة Codex، ثم يُفتح الرابط في Chromium ويُختبر. لا نطلب تغيير سياسة الشبكة إلى unrestricted. إن أردت إدارة الحساب من البيئة لاحقًا فصلاحية الحساب والشبكة خطوة مستقلة؛ لا حاجة إلى كشف أسرارك في النص.

## التحديث التلقائي والمراجعة

مسار العمل المقترح: فرع تطوير ← Pull Request إلى main ← نجاح `V Lex Pro acceptance / acceptance` ← مراجعة المستخدم ← الدمج الموافق عليه ← Cloudflare يبني main وينشره تلقائيًا ← فحص رابط الإنتاج وتسجيل النتيجة.

سير `.github/workflows/pages.yml` الجديد **اختبارات فقط، ولا ينشر GitHub Pages**. يحل محل السير القديم الذي نسخ قائمة ملفات لا تشمل المنصة الجديدة. يتحقق من lockfile والثغرات والأسرار وتاريخ الملفات والأرشيفات، ثم مجموعات القبول واختبار النقل بين origin مختلفين. أدوات CI مثبتة بإصدارات وSHA معروفة، وصلاحياتها contents:read، ولا أسرار نشر أو id-token. تحفظ سجلات الفحوص 14 يومًا ولا ترفع أرشيف المصدر أو نسخ المستخدمين.

**إعدادات GitHub التالية مقترحة ولم تُطبق:** قاعدة حماية main تتطلب PR ونجاح check باسم acceptance وتحديث الفرع قبل الدمج، وتمنع force push وحذف الفرع. اجعل المراجعة بشرية قبل الدمج. إذا توفر مراجع ثانٍ فعّل موافقة واحدة؛ لا تفترض إمكانية موافقة صاحب PR على طلبه بنفسه. لا auto-merge قبل اعتماد المستخدم. يظل تطبيق القاعدة بحاجة توضيح وموافقة على إعدادات المستودع.

بعد نجاح Cloudflare، يمكن اقتراح تعطيل GitHub Pages القديم حتى لا يبقى رابط آخر قديمًا؛ هذا تغيير إعدادات لم يُنفذ، ولا نوقف رابطًا حاليًا قبل التحقق من البديل.

Cloudflare لا تنتظر GitHub Actions تلقائيًا؛ حماية main هي التي تمنع وصول تغيير فاشل إلى الإنتاج. بعد الدمج المعتمد، فعّل automatic production deployments لmain. اجعل المعاينات Custom branches مثل فرع التجهيز الحالي و`preview/*` والفروع الجاهزة التي تختارها، بدل نشر جميع الفروع القديمة. هذه إعدادات مقترحة حتى يُربط الحساب وتُراجع الواجهة الفعلية.

## قبول الإنتاج بعد النشر

```sh
node platform-tests/deployment/hosted-acceptance.cjs \
  --url https://ACTUAL_PRODUCTION_HOST \
  --output /tmp/vlex-production-check
```

القيمة في المثال placeholder وليست رابط موقع. الأمر يطابق manifest وبصمات جميع ملفات التشغيل المقدمة عبر HTTP مع البناء المحلي المتوقع (عدا _headers الذي تعالجه Cloudflare كإعداد)، ثم يفتح العنوان الحقيقي بملف متصفح جديد، ويتحقق من الدروس والمشاريع وRouter وCSS/JS والمحاكي والثيمات والجوال والحفظ بعد إغلاق المتصفح، والتصدير والاستيراد من origin محلي مختلف ورفض ملف تالف. لا يستعمل بيانات المستخدم الموجودة. لا يكفي نجاح build أو ظهور deployment أخضر لإعلان نجاح النشر.

قبل الاعتماد النهائي للصوت، اختبر سماعيًا قناتي المحاكي والنطق على جهازك؛ توفر أصوات SpeechSynthesis يعتمد على النظام. نُفذ قياس رقمي لقناتي المحاكي، ولم يُدّع اختبار سماعة فعلية أو صوت إنجليزي محلي غير متاح.
